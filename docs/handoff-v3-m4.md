## 背景：真机验收暴露的产品缺口

owner 用工作群连续截图跑完整流程后的结论：

- ✅ OCR 提速、归并、排序、时间不推测全部生效——v3 主链路通过
- ❌ 「几月几号去哪、带什么材料」「文件格式要求」这类内容只能折叠成某个联系人名下的一段备注，
  **没有时间信号的连卡片都不出**——事情本身没有独立存在的位置
- ❌ 群聊里的推进碎片（「荀导已到」「王总到了」）是某个已有事项的状态更新，现在只能散落在人的互动记录里
- ❌ 重传同一批截图：联系人卡片正确显示「更新联系人＋差异」，会议却仍是「新会议」，不提示已存在
- ❌ 截图自带的时间戳分隔行（如「8月12日 09:30」）没被利用：其下消息里的「今天下午14:30」
  被留空（符合 M3 规则），但**日期明明写在截图里**，照抄不算推测
- ❌ 批量处理的耗时大头已从读图挪到归并：每个精确匹配不上的称呼（简称、称谓、@提及）
  都要一次 LLM 往返，一批群聊截图十几二十次

## ⚠️ 本批的地基约束：现有安装库没有迁移机制

`app/src/local/store.ts:174` 与 `server/src/db.ts` 都只跑一遍 `MAILUO_SCHEMA_SQL`，
全部是 `CREATE TABLE IF NOT EXISTS`——**对已存在的表什么都不做**。owner 手机上的库
已装着真机验收数据，不能推倒重来。这带来两条硬约束：

1. **任何新列都必须走迁移**（Goal 1 会建这套最小机制，本批其它 Goal 踩着它走）
2. **`action_cards.type` 的 CHECK 约束（schema.ts:28，四个值）在旧库上改不了**——
   SQLite 不支持修改已有表的 CHECK；12-step 表重建对工作层数据不值得。
   **所以本批不新增卡片类型**，查重走 payload 内字段（见 Goal 2）。

⚠️ 这里有一个 M1 同款的测试陷阱：Node 测试每次新建库、恒走新 schema，**测不出旧库路径**。
迁移测试必须真的先按旧版结构建表、再跑迁移（Done when 第 3 条是红线）。

## Goal

### 1. 事项模型 + 最小迁移机制 —— 地基，先做

**现状**：感知层的 `kind` 枚举本来就有三值（`perceive.ts:40`：meeting / appointment / other），
是在 propose 层被扔掉的——`propose.ts:446`（`buildMeetingCard`）见到非 meeting/appointment
直接返回 null，`propose.ts:494`（`shouldFoldEventIntoInteraction`）把它们折叠进参与人的互动记录；
没有时间信号的 meeting/appointment 也同样折叠。

**改成**：

- **迁移机制（最小实现）**：`PRAGMA user_version` 版本号 + 顺序执行的迁移数组，
  放在 `shared/core/`（schema.ts 旁），app 的 `store.ts` 与 server 的 `db.ts` 初始化时都跑。
  v1 迁移：`ALTER TABLE meetings ADD COLUMN kind TEXT NOT NULL DEFAULT 'meeting'`。
  kind 合法值在代码层校验，**列上不加 CHECK**（留改动余地）。
- **`buildMeetingCard` 放开**：三种 kind 都出卡，kind 原样落库；时间门槛去掉——
  无 `time_iso` 且无时间信号也出卡（`time_iso: null`）；参与人允许为空
  （schema 本就默认 `'[]'`）。
- **`time_text` 的 NOT NULL 兼容**：纯待办可能没有任何时间文本，存空串；
  UI 见空串**隐藏「聊天里的时间」那一行**（`meeting-list-card.tsx`），不显示空值占位。
- **折叠逻辑收窄**：凡出了独立事项卡的 event，不再折叠进互动记录（避免同一信息双份）；
  参与人自身的 `interaction_summary` 不受影响照旧。若发现现状互动记录里有依赖折叠才存在的信息面，
  在报告里说明取舍，不要静默丢。
- **UI 区分**：日程页（`meetings.tsx`）与卡片按 kind 区分文案——meeting/appointment 维持现状，
  other 显示为「事项」口径（具体措辞你定，别再叫「会议」）。无时间的事项排序：
  排在有时间事项之后或单独分组，你定，报告里说明。

### 2. 事项查重提示（M3 的 3b 移入，判据按事项重新设计）

**照抄联系人那套的形状**：resolve 判 `same_as` → `buildContactChanges` 算差异 →
差异为空跳过 / 有差异出 `update_contact` 卡（`propose.ts:824` 附近）。

事项版：propose 出新事项卡前，与库里已有事项比对；判定「已存在」时，卡片变成
「已有相似事项 → 是否更新」并展示差异。**不做自动去重**——提议 + 人工确认是本产品哲学。

- **不新增卡片类型**（CHECK 约束，见上）：复用 `create_meeting` 卡，payload 增加
  `duplicate_of_meeting_id` 与差异描述；UI 见此字段渲染「已存在→是否更新」；
  execute 见此字段对目标行做 UPDATE 而非 INSERT。如果你认为这条绕法有更好的替代，
  报告里提方案，**不要自己去扩 CHECK 约束**。
- **相似判据从保守起点开始**：同 kind 且标题归一化相等 → 判重；标题高度相似且时间同日 → 判重。
  泛化后的事项可能既无时间也无地点，所以判据主轴是标题。阈值与规则要可调、
  并在代码里写清选择理由（M3 惯例）。**方向死线：宁可漏判重（多出一张新卡）
  也不要错判重（把两件不同的事并成一件）。**
- 查重先用纯本地比对（归一化/相似度），不引入额外 LLM 调用；不够用在报告里说明再议。

### 3. 事项可累积（碎片挂靠）

群聊碎片（「荀导已到」「王总到了」）是某个已有事项的推进状态，应能挂到该事项、追加进其备注。
机制与 M2 的 pending contacts 同构，但**碎片没有名字可精确匹配，只能靠 LLM 看上下文**。

- 实现位置在 resolve 阶段新增一步：把**近期未完成事项清单**（标题 + 时间 + kind）
  连同感知产物喂给文本模型，问哪些内容是对已有事项的推进 → 命中的出「更新事项备注」卡
  （复用 Goal 2 的 payload 机制，差异 = 备注追加）；不命中的维持现状（进人的互动记录）。
- **判据死线：宁可不关联也不要错关联。** LLM 置信不高就不出关联卡。owner 原话：
  「（关联不上）人的备注里也留着，不必担心」——信息有两个落点，人的互动记录兜底，
  所以漏关联无害、错关联有害。
- **控制 LLM 开销**（别跟 Goal 5 打架）：挂靠判定一批最多一次往返，且有条件跳过——
  库里没有未完成事项、或感知产物里没有推进类内容时不调用。

### 4. 时间戳锚点

微信截图自带时间戳分隔行。其下消息里的相对时间应锚到该日期——
**这不违反「时间不推测」：日期写在截图里，用它是照抄证据，不是推算。**

**现状**：`app/src/local/perceive-ocr.ts:10` 的 `WECHAT_TIME` 正则只认纯时刻行
（`^(昨天\s*)?\d{1,2}[:：]\d{2}$`），「8月12日 09:30」这种带日期的分隔行认不出。
真机实测：某条会议通知只写「今天下午14:30」，现版留空——符合 M3 规则，
但该截图上方的时间戳行里有绝对日期，锚上就能填。

- **OCR 层**：扩正则识别带绝对日期的时间戳行（「8月12日 09:30」「2026年8月12日 09:30」等
  常见微信形态），把它作为时间锚点标注传给文本模型。先读现状代码看时间戳行现在怎么被处理，
  沿着已有结构做，不要新开一条链路。
- **prompt 层**（视觉版与文本版规则一致）：消息只含相对词（「今天下午」「明天上午」）、
  且其上方最近的时间戳行含**绝对日期** → 按该日期换算出 `time_iso`（时刻取消息里的钟点）；
  截图内没有时间戳行、或时间戳行本身是相对形态（「昨天 09:30」「星期二 09:30」）→
  **维持 M3 行为，`time_iso` 留 null**。相对锚不能当绝对锚用——宁可留空。
- **propose 覆盖层不改**：M3 定的 `resolveChineseTime` 只解析绝对日期，「今天下午14:30」
  它解析不出、会保留模型值，链路自洽。但要有测试确认覆盖层不会把锚定好的值覆盖掉。
- 年份缺失默认当年（M3 规则延续）。

### 5. 归并 aliases 提速（动机 = 省 LLM 往返，不是合并卡片）

**现状**：`resolve.ts` 的 `findExactMatches` 已经同时查 `canonical_name` 和 `aliases`——
机制地基是全的，缺的是 **aliases 没被喂饱**：简称（「王总」）、@提及、称谓每批都精确匹配不上，
每个都走一次 LLM 往返。

两路补喂，判据同一条——**只把「已确认属于同一人」的称呼写进 aliases**：

- **感知层**：同一张截图内有确凿对应证据的多种称呼（如 @全名 与简称同现指向同一人），
  归进该 participant 的 `aliases` 数组（视觉版与文本版 prompt 一致改）。
- **归并回写**：LLM 判 `same_as` 之后，把本次使用的称呼并入 `update_contact` 卡的
  aliases 变更（`buildContactChanges`），用户确认后入库——下一批同称呼直接精确命中，跳过 LLM。

⚠️ **边界（必须守住）**：本条只减少 resolve 的 LLM 调用次数，**不改卡片拆分行为**——
「按截图拆卡片、不提前合并」是 owner 定过的产品行为，之前否决过的正是「卡片层提前合并」。
aliases 的写入全部经用户确认的卡片走，感知层只在同图证据确凿时归组。
